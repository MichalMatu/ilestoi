# Project Instructions

## Host routing for IleStoi.pl only (owner decision, 2026-10-26)

- For implementation, code review, native tests and operational checks concerning **this IleStoi.pl repository**, select the **Android/Samsung Termux Local Agent** explicitly by its installed host/installation identity. Communicate through the private Local Agent host-task transport in `MichalMatu/local-agent` and use GitHub Connector for repository operations. This choice **does not apply to any other repository**; never silently route unrelated projects to the phone.
- The phone already has the repository, application server, SQLite/data, Cloudflare tunnel and production runtime. Reuse the **existing Git object store via an isolated Git worktree** for development; do not require a separate Local Agent project binding for ordinary Host Ops tasks. A project binding is only needed if deliberately switching to the repository-scoped project-task lane.
- The running checkout `~/WreckScanner/WreckScanner` and its SQLite, photos, credentials and service directories are **production**. Do not edit, reset, checkout a development branch in, run destructive tests against, or restart this working tree as part of normal feature development. Use a dedicated worktree beneath `~/.local/state/ilestoi-dev/worktrees/`; verify the production Git HEAD, status and `runit` services before and after potentially impactful operations. Git worktree metadata changes must not move the production HEAD.
- Run JS/Node/Python quality checks on the **Termux worktree first**, with bounded CPU/memory/process limits, preserving headroom for the website. Avoid running expensive parallel tests on the production host. Use MacBook only for a clearly identified platform-specific gap (such as desktop Chrome), not as the default test runner.
- GitHub `main` is the single canonical **released and deployed** source. Work only on short-lived `feature/*` or `fix/*` branches from current `main`, in isolated worktrees. No permanent `work/dirty` or auto-deploy. Review and test candidates before a guarded production cutover; advance `main` to the **exact accepted deployed commit**, tag the release and remove the merged short-lived branch. A candidate merged to `main` before production acceptance would make `main` lie about production.
- See `docs/TERMUX_DEVELOPMENT_FLOW.md` for commands and boundaries. Host selection is explicit; do not build an automatic cross-host scheduler, fallback, repository binding, or change to the Local Agent project router.


- Do not add or preserve redundant backward-compatibility paths. When replacing an internal API, configuration shape, flag, request field, or UI contract, migrate current callers and remove old inputs, branches, constants, comments, and fallbacks in the same change unless explicitly requested otherwise.
- Android Termux production uses standard runit supervision for `wreckscanner`, `wreckscanner-backup`, `cloudflared`, `mosquitto`, `sshd` and `ilestoi-healthwatch`. `~/.termux/boot/00-services` only starts/requests those services; never start `server.py` or the tunnel through a second `nohup` watcher. The private `90-local-agent` is independent. See `docs/TERMUX.md`.
- Verify production via the Termux Local Agent with read-only `sv status` and `127.0.0.1:8001/api/health/live`/`ready`. Do not send live database-write HTTP tests without separate deployment scope.
- Cloudflare Tunnel routing is locally managed on the backend host, not from the Cloudflare dashboard. Add or change public hostnames in `/etc/cloudflared/config.yml`, validate with `cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate`, then restart `cloudflared.service`; create matching proxied Tunnel/CNAME DNS records in Cloudflare for each hostname. **On the separate Termux deployment**, do not use Linux `systemctl`: use the named tunnel `ilestoi-phone` and `runit` per `docs/TERMUX.md`.
- Git flow: keep `main` at the exact production commit. Name short-lived branches `feature/<topic>` or `fix/<topic>`; PR/review before release, guarded deploy of an immutable candidate, then fast-forward `main` to that accepted commit and add a production tag. Do not rewrite deployed history or squash after a candidate has been deployed. Preserve historical commits under immutable archive tags before retiring old branches.
- Release tags are published **on GitHub through the authorized Mac Local Agent with its existing `gh` credential**, after accepting the exact deployed SHA. Termux is not the GitHub release-tag writer; do not install write-enabled deploy keys or PATs on the production phone for tagging. Verify the remote annotated tag object matches its intended local object exactly, with no force-push. See `docs/TERMUX_DEVELOPMENT_FLOW.md`.
- In dense working modals, every visible line must earn its space. Prioritize the actual photo, data, and decisions; avoid persistent instructional copy when labels, icons, tooltips, or transient status messages can carry the same meaning.
